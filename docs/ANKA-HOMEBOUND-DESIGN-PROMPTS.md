## 方向与参考依据

一句话：一个人或与朋友一起，扮演圆润小人，深入失联区域搜集物资、营救幸存者，再带着人和物资安全回营地。

情绪关键词：可爱、未知、轻度紧张、互相照顾、带大家回家。核心差异：救出的人会成为营地居民，解锁设施、路线和后续故事。

## 使用方式

1. 将下面的「游戏设计总 Prompt」整体交给设计或开发模型，生成详细 GDD、原型任务和数据表。
2. 使用 GPT Image 时，每次发送「统一视觉前缀」加上一个具体出图 Prompt。每个编号单独出图。
3. 先确认角色母版，再制作换装、场景和宣传图。后续出图时，把确认过的角色母版实际附上，并声明为身份与比例参考。
4. 图像用于概念和资产制作参考；3D 模型、骨骼、动画、界面布局及交互需在项目中单独制作。图像模型输出的多视图仍需人工核对一致性。

## 游戏设计总 Prompt

```text
你是一名熟悉浏览器 3D 游戏的游戏总监、系统策划、关卡设计师、美术总监和 Vue / Three.js 技术负责人。

请依据以下确定的方向，为原创游戏《ANKA：归途小队 / ANKA: Homebound》（暂名）撰写一份可执行的完整游戏设计文档 GDD，并附上分阶段开发任务、初始数据表与验收清单。

请直接进行具体设计。不要只罗列可以选择的方向；对未确定的常规问题给出一个推荐默认值并注明假设。所有数值标为初始调参值，性能指标标为待实机验证的目标。先完成设计文档，不立即修改现有项目。

一、平台与已有项目边界

1. 必须采用 Web + Vue 3 + Three.js + Vite，浏览器打开即可玩。原型优先复用 outpost-strike 熟悉的 JavaScript ES Modules 结构，不为策划阶段额外迁移整套技术栈。
2. Vue 负责菜单、HUD、背包、任务、营地、设置和房间界面；Three.js 负责场景、相机、模型、动画、战斗表现。实时模拟状态独立于 Vue 响应式界面，界面按需订阅变化。
3. 优先支持电脑浏览器；兼容手机和平板横屏直接游玩。手机作为独立手柄时，手机只传输输入，不需要渲染 3D 游戏。
4. 以 WebGL 2 为基础；不依赖 WebGPU。采用可调画质、按地图加载、可压缩 GLB 资产、共享纹理、实例化和对象复用。
5. 联机可以依赖 Anka 后端：浏览器免安装不等于双人联机无需服务端。独立开发入口能玩单人；房间、访客邀请、设备接入复用 Anka 的授权和传输能力。
6. 参考 outpost-strike 的设备接入、输入路由、房间、角色动画、寻路和资源压缩实现，列明可直接复用、需要适配、需要新建的模块。避免直接把已有 PvP 规则视作已经支持 PvE 合作。
7. 现有项目的真人联机主要是双人 PvP，合作玩法主要使用 AI 搭档。新游戏的真人双人 PvE、营地进度、救援与战利品结算都需要明确新增设计。
8. 作为独立游戏模块或独立项目规划；不覆盖 outpost-strike 的玩法与手柄配置。房间、设备授权、存档必须有独立游戏命名空间。

二、游戏定位与核心支柱

类型：可爱人形角色、俯视角 3D、PvE 探险收集、幸存者救援、轻度撤离、营地成长。
玩家：喜欢探索、收集、换装、合作和适度战斗的玩家。单人完整可玩，双人合作增强互助感。
核心体验：在有风险的陌生地方发现资源和求救信号，权衡继续深入或带人回家。

确定五个支柱：
A. 每次出发都有可理解的小目标，12–18 分钟完成一局主要探索。
B. 探索依靠路径、地标、声音与环境线索，不被满屏任务箭头替代。
C. 救援带来永久可见的营地变化；被救者有名字、工作和后续联系。
D. 同一套角色动作、武器和工具适用于单人、双人及不同输入设备。
E. 圆润角色、模块换装、低成本可扩展的 3D 风格，适合浏览器稳定运行。

三、世界观与原创识别

背景：群岛边境因一次能量设施事故发生通信中断和机器失控。救援队从一座旧中转营地出发，寻找幸存居民，恢复供电与航路。
角色是原创的简化人形，不是鸭子或狐狸；通过职业服、帽子、头饰、眼镜和背包形成身份。
气氛是温暖营地与神秘野外的对照。战斗使用可读的卡通表现，无写实伤口。
提出统一原创符号：小屋轮廓中嵌一枚四角导航星，用于营地旗、救援背包和撤离信标。
输出：世界背景、玩家身份、当前危机、营地的意义、前三位可救 NPC、主线推进与第一章结尾。

四、核心循环与一局节奏

局外：与居民交谈 → 选择任务与路线 → 整理装备和背包 → 单人出发或邀请好友。
局内：抵达入口 → 探索与搜集 → 战斗或绕行 → 找到幸存者 → 稳定伤情 / 恢复道路 → 护送或背负 → 激活撤离点 → 安全撤离。
回营：结算带回的人和物资 → 居民入驻 → 建造或升级设施 → 解锁蓝图、外观、任务和下一条路线。

给出一段完整的约 15 分钟例局，逐段写清时间、路径、敌人、物资、救援目标和撤离选择。
不要求每局必须救人：自由搜集、发现线索与升级准备也构成有效进展。主线救援有较高权重，不能被无限刷普通敌人取代。

五、视角、移动与战斗

1. 使用固定方位的 3D 俯视 / 等距感相机，原型可用正交相机，俯角约 50–60 度。默认不自由旋转世界相机。
2. 移动方向基于屏幕方向映射到地面，瞄准方向与移动独立。鼠标投射到地面取得目标方向，手柄通过触控或相对体感控制地面朝向。
3. 角色有移动、短跳、翻滚、开火、精瞄、换弹、武器切换、投掷、工具 / 护盾、治疗、交互。短跳用于矮障碍和少量路线变化，不做复杂平台跳跃。
4. 提供适度瞄准辅助，不隔墙锁敌；敌人的攻击预警和优先威胁清晰。降低操作复杂度，而不是依靠更高伤害自动获胜。
5. 首版战斗限于单层地面和矮台阶，避免多楼层瞄准歧义。遮挡的屋顶、树冠和前景物体淡出；敌人不被 UI 或屋顶永久遮住。
6. 武器首版三类：通用短射程连发器、近距散射器、低射速精准器。提供差异化射程、弹匣、换弹、声音和弹药经济，采用可读的卡通装备外形。
7. 工具首版三类：扫描器、护盾装置、急救包；投掷物首版烟雾与诱饵中的一种。避免大量枪械改装和复杂伤口模拟。
8. 敌人首版三类：巡逻近战机、远程警戒机、呼叫支援的侦察机；精英使用重型维修机。输出感知、预警、追击、失去目标、返回和救援区交战规则。

六、单人与双人合作

首版模式：单人，以及两位玩家各自在浏览器运行游戏的双人在线 PvE。双方可以分别使用键鼠、手机手柄或本机触控。默认关闭友伤。
同屏双人、两部手机分别控制同一画面中的 P1/P2，是后续阶段的扩展；须新做按玩家槽位分流的输入绑定和共享相机，不能声称现有一人一设备实现已支持。

单人不强制带 AI 队友；任务机关、护送和搬运都要有单人完成路径。双人能分工开路、警戒、治疗和救人，但不设置必须两个真人同时按住的主线机关。
建议双人敌人数约为单人的 1.3–1.5 倍，精英生命约为 1.4–1.6 倍，均作为待调试起点；不得简单翻倍所有生命和伤害。

倒地与恢复：双人倒地后给予约 45 秒救助期，队友可进行约 4 秒的连续救助；单人默认携带一次消耗型自救机会。救助被移动或受击中断。自救与援助不重复刷收益。
失去救助机会的玩家仍保有安全袋和已提交的永久进度；队友若成功撤离，可保住自己的背包和团队救援结果。禁止一人死亡强制删除另一人已成功带出的东西。

联机规则要写清：建房、邀请、准备、统一开始、共享任务、独立背包、唯一世界掉落、同时拾取裁定、任务道具、分开撤离、倒地、团灭、离开、断线和房主退出。
默认不允许战斗中途加入。短暂失联冻结当前敌人和角色最多约 30 秒等待重连，超时后按预先定义的中断规则结束；首版不做房主迁移。
访客断线可重连原席位；刷新导致权威模拟丢失时，以已保存的出发检查点回营，局内尚未结算收益不入账，出发装备恢复且不重复保留消耗品产物。明确防止回档复制。

七、救援系统：本作的主要差异

首版包含两种：
A. 被困者：搜索到求救信号，解除门锁或修复供电，幸存者随后跟随。
B. 伤员：使用急救包完成稳定处理，然后护送；无法行走的短路段允许背负搬运。

首版每局最多一个任务幸存者，避免队伍和寻路负担。幸存者状态为：待发现 → 已发现 → 已稳定 / 已解困 → 跟随 / 搬运 → 已进入撤离区 → 已成功带回；另有暂时失散和任务未完成分支。
交互键单击开始读条，再次单击可取消；移动、超距、受击和目标变化取消。此规则适配现有手柄的一次性 interact 动作，不假设它已提供持续按住交互输入。
跟随者会避开火线、停在掩体附近，导航失败时先寻路或等待召回；禁止穿越未开门和障碍自动传送到安全区。提供脱困机制和可见反馈。
背负时移动约降低 20%，限制使用双手武器；可放下伤员战斗。单人路线保证可先清敌、放下、推进；不强迫单人同时搬人和执行双手机关。
NPC 不在队伍之外默默永久死亡；倒地进入可再次稳定的状态。未撤离则下次任务可再救；具体失败反馈要保留紧张感而不造成反复折磨。
被救 NPC 为营地增加可见设施，例如医生解锁诊所、维修师修复工作台、向导开放新捷径。

八、收集、物品、损失与成长

1. 首版使用简洁背包格位，不做物品旋转俄罗斯方块。默认 12 个普通格，2 个安全袋格；同类基础材料可堆叠。
2. 物品分类为材料、补给、功能装备、蓝图、收藏品、任务道具。任务道具有独立任务栏，不挤占普通背包；世界中的同一物品只能被取得一次。
3. 初始五类材料：金属件、布料、电子件、医疗草、能量电池。输出获取地点、堆叠量、基础用途、消耗去向。
4. 每人独立携带普通物资；任务完成与救援在任务结算中共享。任务关键物品绑定任务状态，不允许留在断线玩家身上软锁进度。
5. 默认失败丢失本次未放入安全袋的普通战利品；永久外观、已解锁蓝图、已入驻居民和已提交营地进度保留。基础出发装备可保留，避免首版的装备永久损失让新玩家破产。
6. 安全袋仅保护小型普通材料，不收任务幸存者、任务关键道具和大件装备。开局自救资源和普通补给仍按正常消耗结算；系统中断回档另行处理。
7. 共享营地属于房主世界。访客获得自己的已撤离物资、蓝图 / 外观解锁，以及已经共同完成的救援任务凭证；回到自己营地后可兑换同一 NPC 的入驻资格，不重做同一救援。营地建造、设施等级与花费不自动复制。定义任务 ID、重复救援奖励和幂等规则。
8. 外观与功能装备分离：帽子、眼镜、衣服、挂件和换色不改变数值；护具、工具、背包容量由独立功能槽决定。允许外观覆盖，但玩家仍能识别队友与战斗状态。
9. 三种成长：局内路线知识与材料收益、局外设施和功能蓝图、长期服装与营地装饰收藏。首版不做饥饿口渴、耐久修理税和多层随机词条。

九、营地与内容规模

营地采用固定位置逐步修复，不做自由摆放建筑。
首版五个点位：任务板、仓库、工作台、诊所、衣柜；居民入驻让空间更丰富，点亮灯、开店、增加日常动作。
每次升级写清材料成本、结果、下一步目标，不用只有百分比的升级撑满成长。

完整第一章规划三片区域，但首版只做第一片：
1. 苔林中转站：森林、旧站房、小溪、维修棚；教学与首个救援。
2. 潮汐旧港：仓库、码头、潮道；后续中期内容。
3. 雾岭能源站：风雪、通信塔、封闭设施；后续高风险内容。

第一片地图是手工制作的主路径与地标，加上有限随机的资源、敌人巡逻和事件。要求约 120×120 米作为原型尺寸起点、两条可选路径、六个明显地标、一个主救援区、两个撤离点。
避免首版无限世界、复杂程序化地形和完整实时天气。随机内容必须受任务可达性、资源可获取性和撤离可用性约束。
两个撤离点分别为较安全但路远的营地车站与靠近高价值区但需要电池激活的信标平台。默认不设强制整局倒计时；信标启动后有约 20 秒可见撤离读条和小规模敌人压力。
允许独立撤离：按每位玩家进圈并完成读条判定其背包，NPC 归属按共同救援任务记录处理；不能因另一人还在地图就无故扣回已成功撤离收益。

十、人物和美术规范

1. 原创角色共用三头身简化人形骨架。整体高度约等于三个头高：头高 1、头以下躯干和骨盆约 1.2、腿和脚约 0.8。
2. 头是圆角方形与椭球之间的形状，身体圆润但头、躯干、手臂、双腿分离清楚。保留肩肘、髋膝的运动结构，使用圆手和简化鞋；无需五指、写实皮肤和肌肉。
3. 面部以两枚深色椭圆眼和极小鼻子为主，默认不画嘴部细节。发型以整块轮廓表现。身体比例、关节位置和脸部布局在所有外观中保持一致。
4. 第一套为橙色短探险夹克、深青裤、软帽、透明圆护目镜、小救援包；第二套为青绿色短夹克、米白裤、圆顶救援帽和同规格背包。两人共用同一个基础身体。
5. 玩家通过外观轮廓、名字、P1/P2 形状标记和队友轮廓共同识别，不只依赖颜色。
6. 模块外观槽：发型、帽子 / 头饰、眼镜、上衣、下装、鞋、背包外观、挂件。帽子可隐藏部分头发，眼镜与帽檐有兼容规则；长衣和大背包需要碰撞与动画遮挡检查。

8. 环境为苔绿、石灰、深青；救援目标偏暖黄，危险预警为珊瑚红。夜景也要保留道路与攻击预警的可读性。

10. 必要动画：待机、走、跑、短跳、翻滚、持武器、开火、换弹、受击、倒地、救助、搬运、放下、交互、庆祝；共用骨架并明确叠加层和上半身动作。

十一、手机手柄与三种输入路径

必须区分：
A. 电脑运行游戏，手机扫码打开专用网页手柄，沿用 Anka 的设备授权、绑定和 WebSocket 输入 / 反馈路径。
B. 手机 / 平板自身运行游戏，使用横屏触控 HUD。左移动，右侧瞄准与开火和少量动作按钮。
C. 电脑键鼠。所有输入最终进入同一套游戏动作语义。

现有独立手机手柄的真实结构：上方两个主键，左开火 L、右瞄准 R；四个反馈灯；下方九宫格。九宫格第一排为换弹 / 切换武器 / 手雷，第二排为护盾 / 中央圆形跳跃 / 治疗，第三排为翻滚 / 交互拾取 / 蹲伏。
中央区域拖动负责移动，短点负责跳跃；顶排横滑负责转向，短点仍触发各格功能。体感可校准并选择只在按住瞄准时工作，也有触控观察后备。

为本作设计独立的游戏手柄配置，保持上述布局与手势习惯：底右格可在新配置中改为背包，顶部手雷可显示为投掷，护盾格显示为工具。背包必须采用新增、经过能力协商的 inventory 动作；不把旧 toggle_crouch 无声改成背包，不能破坏 outpost-strike。
其余现有协议字段 move、look、pose、turnTotal、buttons.fire / aim，以及 reload、next_weapon、grenade、shield、jump、heal、roll、interact 等动作可以经适配器复用。新增动作和反馈标为新增，协商失败时给出明确降级路径。

固定俯视相机下：
- 移动始终按屏幕坐标映射地面，不随着角色朝向旋转。
- 手机相对体感 yaw 控制角色在地面的瞄准方向；重校准对齐当前朝向。pitch / roll 默认不旋转世界相机。
- 顶排滑动转向用于改变瞄准方向或调整参考朝向；原射击游戏的一格 180 度灵敏度在本作配置中可降低并独立调节。
- 未开启传感器权限时可全触控完成；不强制体感。手机网页手柄的关键操作不依赖标准蓝牙手柄或额外安装 App。
- 九宫格拖动和短点必须互斥，拖动结束不补发跳跃、换弹或投掷。

背包 / 菜单开启时切换输入上下文：中央拖动改为格位导航，开火键确认，瞄准键返回；关闭界面并等待按键释放后再恢复射击，防止确认动作误开火。双人中打开背包不暂停世界，单人可暂停。
救援进度、目标和读条显示在主游戏画面；手柄保持控制器界面，不增加一套重复的生命和弹药 HUD。
沿用中央圆按钮绿色环表示连接、红色环表示断开，并加图标 / 可访问文本，不仅用颜色传递状态。反馈灯用于受击、完成等短反馈，震动能力不可用时有视觉后备。
输入过期、手柄断线、页面隐藏、暂停、切换输入设备、旋转屏幕时，移动和持续开火立即清零。已有输入过期阈值可作为起点；等待中立输入后才重新获得控制。
每位在线玩家先加入自己的浏览器席位，再为该席位单独绑定手机；房间邀请二维码与手柄绑定二维码必须清楚区分。

十二、界面与无障碍

设计以下页面与状态：开始页、存档 / 继续、营地、任务选择、双人大厅、两类二维码接入、加载、局内 HUD、背包、救援读条、撤离、结算、衣柜、设置、失联等待与错误恢复。
HUD 保留：生命与队友状态、弹药、当前救援目标、简洁小地图、交互提示、撤离状态。战斗区域不被常驻大面板覆盖。
支持中文、字体缩放、色觉差异、相机震动关闭、低闪烁、音量分项与触控按钮尺度调整。重要信息同时使用形状、文字或音效中的第二种信号。
输出桌面、移动横屏、独立手机手柄的布局差异和输入状态切换表。

十三、浏览器架构与持久化

建议模块：GameSession、World / MapLoader、Actor、InputRouter / InputContext、CameraRig、CombatSystem、EnemyAI / Navigation、LootSystem、Inventory、RescueSystem、ExtractionSystem、Camp / Progression、NetworkAdapter、SaveStore、AssetLoader、Audio / Feedback、PerformanceMonitor。
给出模块职责与事件流，不要求为命名强行新建大量类。可以沿用现有项目习惯。
主机浏览器模拟 AI、战斗、物品和救援的局内事实，Anka 验证成员身份并转发；客人发送输入 / 动作请求。每个掉落有唯一 ID，拾取采用一次性裁定。恢复连接发送完整必要状态，避免补放过期射击。
场景状态与视觉效果分开同步；预估 15–20Hz 权威状态更新，显示端插值，必要时加本地移动预测并处理纠正。注明这是双人好友原型的默认方案，不承诺竞技级反作弊。
永久存档与任务结算走服务端幂等记录；会话、出发快照和结算事务关联唯一 expeditionId。明确重复提交、断线重提、半途撤离、团灭、系统中断的结果。首版不信任客户端直接提交永久货币数量。
独立单人使用 IndexedDB 保存进度；Anka 账号模式使用服务端存档并辅以本地缓存。设计存档版本迁移和冲突处理，不将临时访客身份等同于永久账号。
营地固定升级、居民入驻、外观解锁与背包分别记录。访客离开前可导出或转移自己的本地进度；具体账号接续作为单独需求说明。
浏览器声音与体感权限在用户操作后启用，无法全屏或锁横屏时给出可用布局。加载失败可重试，离开关卡释放资源；处理 WebGL context lost 和版本不一致。

十四、画面和加载预算

以桌面 1080p 60FPS、手机约 720p 内部渲染 30FPS 为原型目标，达标需实机测量，不预先宣称保证。
首版低画质初始预算：可见三角面约 15–25 万、draw calls 约 100–150、同屏活跃敌人约 8–12、实时投影光源最多一个；基于测试再调整。
角色单体基础模型约 5k–8k 三角面，连服装和背包建议控制在 12k 内；常规小道具约 200–1500。贴图优先共享 512 / 1024 图集，主角特殊需求单独评估。
首个可交互营地必需下载量争取压到 8–12MB，首张探索地图再按需加载；该目标按压缩后实际传输量测量，并记录解码与 GPU 上传时间。
采用 Meshopt 等已有项目支持的模型压缩、WebP 等贴图处理、重复植被实例化、碰撞简化、纹理复用与距离裁剪。烘焙或顶点环境色配合少量实时光照。
手机降低像素比、阴影分辨率、粒子和植被密度；不把重景深、体积雾、全屏发光和高分辨率透明层设为基础需求。
测试矩阵至少包括桌面 Chrome / Edge、macOS Safari、Android Chrome、iOS Safari；每类注明实际测试设备。未测试的项目标为未验证。
```

## 后续迭代短 Prompt

角色一致性：

```text
保持附图角色的头身比例、头型、眼睛位置、鼻子、肢体长度、手脚大小、材质和相机不变。只将当前上衣替换为青绿色短救援夹克，帽子替换为圆顶救援帽，裤子替换为米白色。背包大小和接口不变，不添加新道具或背景，不改变角色物种与骨架。
```

减少场景制作成本：

```text
保持附图的路径、地标、人物位置、镜头和配色关系不变。将环境简化为更适合实时浏览器渲染的低多边形资产：减少植被数量和叶片层数，合并微小碎石，去掉体积雾、重景深和细密表面纹理；保留关键掩体、救援目标和撤离信标的可读性。不要改变关卡的通行关系。
```

增强角色可读性：

```text
保持相机、场景、人物比例、衣服设计与数量不变。仅改善人物与地面之间的明度和色相分离、简化人物附近杂物、加强脚下接地阴影，并让玩家、幸存者和敌人的轮廓更容易从固定俯视视角分辨。不要加粗黑描边，不增加文字、UI 或额外特效。
```

## 出图检查

- 角色比例和面部是否与母版一致；手臂、腿、道具与背负姿态是否合理。
- 换装是否依赖衣服和配件，而非每次重新发明一套身体。
- 实机目标图是否使用能看清路径、敌人和救援对象的俯视镜头。
- 环境是否能拆成轻量模块和重复资产；没有把电影光影当成基础渲染要求。
- 独立手机手柄图和手机直接游玩图是否明确区分。
- 输出是否仅为概念图；需要建模、绑定、动画、界面实现和性能测量的部分是否仍明确列出。
